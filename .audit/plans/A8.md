### D4. The account seam (§4.7, §5.6 items 5 and 6): what the server does

- One `Door43Client` per app, built at start from `AppConfig.door43` and the app's
  `InternetSwitch`. A client that cannot be built (`Door43Error::Setup`, no TLS backend) does not
  stop the app (the translator can still work offline): it is kept as `Err(reason)` and each account
  step that needs Door43 answers `ApiError::Internal` with a report naming the reason.
- **Sign-ins and resumes take one async lane** (`tokio::sync::Mutex<()>`), as tC4's `signInFlight`
  and `pendingResume` make them: a second sign-in waits for the first, never `Busy`. `mint_token`
  lists, deletes and re-creates the token named `translationCore`; two at once could delete each
  other's token at Door43. Amend AD31: "sign-in waits for the one in flight (tC4's `signInFlight`)
  instead of answering `Busy`; `FlowRequest::SignIn` stays for the flows that must not run beside a
  sign-in." (Leave `FlowRequest::SignIn` in place; A3's tests use it.)
- **Cancel stops the sign-in and changes nothing** (amend §5.6 item 6). tC4 lets a cancelled
  sign-in run to its end, then signs out (which also forgets the keychain). Here
  `account/cancelSignIn { signIn: <its RequestId> }` cancels it wherever it is: not yet arrived
  (the id is remembered, the last 16, and the sign-in sends nothing when it comes), waiting for the
  lane, waiting for Door43 (the mint's future is dropped), or in its keychain step (the token it kept
  is forgotten again). A cancel that comes after the sign-in ended signs out the session that
  sign-in made, and forgets the token if that sign-in kept it. End state in every timing: nobody is
  signed in by that sign-in and no token it minted is kept. Declared difference (AGENTS.md "Matching
  tC4"): the next sign-in does not wait for Door43's answer to the cancelled one, and a cancelled
  sign-in no longer empties the keychain of a token an earlier session kept; the person sees the
  same "not signed in", sooner. Record it in §5.6 item 6.
- **Resume uses the token read at start** (A3's rule: the keychain is read once, because an OS
  keychain can prompt the person). Outcomes as tC4's `ResumeOutcome`: `Resumed` (session set),
  `NoneKept`, `Refused` (401/403: forgotten in memory and keychain, notice `savedRefused`),
  `Unavailable` (any other failure, the switch going off included: the token stays, notice
  `savedUnchecked`). A sign-out or a sign-in that lands while a resume waits for Door43 wins: the
  resume restores nothing (a revision counter, tC4 session.test "does not restore a session after
  Sign out while Door43 replies").
- **The first Door43 step resumes the kept token** (§5.6 item 6): `App::door43_session()` returns
  the session, or resumes, or `NeedsSignIn(NotSignedIn | TokenRejected)`; `App::door43_refused(&
  Session)` is what a step calls on 401 (forgets both copies when they are that token, answers
  `NeedsSignIn(TokenRejected)`). Public, documented and tested in A8, used from B9b on.
- **Keychain calls run on the blocking pool** (`tokio::task::spawn_blocking`), never under a lock:
  an OS keychain (E1a) can block on a prompt. The start's single read stays synchronous in
  `App::start` (A3).
- **Reports** (`ReportOp::Share`, tC4's `op: 'share'`, facts `step: "sign-in"`): ok →
  `{step, kept, keepError?, forgetError?}`; refused → `ReportOutcome::Refused { code, key }` with
  facts `{step, status}` (the HTTP status when Door43 answered). Never the login, the username, the
  email, the password, the token or Door43's message (it can name the account). A forget that fails
  at sign-out adds a `ReportOp::Keychain` failure.

### D6. `test/keychain` and `test/reset` (design fix §5.8, §3.9)

- `test/keychain { request, mode?, holds?, relaunch }` → `KeychainView { mode, holds, keeps,
  reads, forgets }`: sets the test keychain's mode and contents, and with `relaunch` reads the
  account again as a launch finds it (sign-ins in flight cancelled, session forgotten, notice
  cleared, the keychain read once, an `Account` frame). The token never comes back in a view.
  Journeys use it for "a sign-in kept on this computer at launch", "a keychain that cannot forget",
  "no keychain" and "the next launch", which tC4's journeys do with `fakeKeychain` and a reload.
- `test/reset` also resets the account: sign-ins in flight cancelled, the test keychain back to
  working, empty, counters zero, the account as a launch finds it. Without it a sign-in in one
  captured screen leaks into the next (`home()` is `test/reset`).
- `AppDeps` gains, under `feature = "test-hooks"`, `test_keychain: Option<Arc<MemKeychain>>`: when
  given and the hooks are on, it is the app's keychain (it replaces `keychain`) and the one the hooks
  set. tc4 sets it with `--test-hooks`.
- Rename in §5.8: `test/door43`'s row says "(A8: the fake runs as its own process with a control
  port on loopback that tests call directly; R13's dropped connection, when E1a adds it, goes there)".

Handlers and their exact behaviour:

- **`account/signIn`** (`Handle<SignIn>`, NET `signIn` is checked by dispatch before):
  1. `let cancel = account.arrive(req.request)`: under `sign_ins`, a `CancelToken`, already
     cancelled when `early` holds the id; inserted in `running`. A guard removes it on every return.
  2. `login = req.login.trim()`; empty login or empty password → report refused, answer
     `Refused(SignIn(AuthFailed))`, no request (tC4 `share.auth-failed` "enter your Door43 username or
     email and your password"). `Credentials::new(login, Password::new(req.password))` refusing
     (`:` or a control character) → the same `AuthFailed`. The password is never trimmed.
  3. `tokio::select!` on `lane.lock()` and `cancel.cancelled()`; cancelled → answer `Ok(view)`
     (nothing sent).
  4. The client (`door43.as_ref()`; `Err` → `self.internal(...)`).
  5. `tokio::select!` on `client.mint_token(&credentials, &TokenName(TOKEN_NAME), &TokenScope::FOR_SHARING)`
     and `cancel.cancelled()`; cancelled → `Ok(view)` (the future is dropped: whatever Door43 did,
     nothing is kept).
  6. `Err(e)` → `let refusal = sign_in_refusal(&e)`; report `Refused { code, key }`, facts
     `{step: "sign-in", status}`; answer `Refused(SignIn(refusal))`. Nothing changes.
  7. `Ok(session)` → keychain on the blocking pool: when `req.stay && keychain == Works`, `keep`;
     on `Err(NoKeychain)` the state's keychain becomes `Missing` and `kept` becomes `Refused`; on
     another `Err` `kept` becomes `Refused` and `keepError` goes in the report. When not kept,
     `forget` (tC4 #366: an earlier kept token must not sign the next session in); a failed forget
     leaves `kept` as it was (the keychain still holds a token: the truth) and adds `forgetError`.
  8. Commit, lock order **`sign_ins` then `state`** everywhere: if `cancel.is_cancelled()`, drop the
     result, and if step 7 kept the token, forget it again (blocking pool); answer `Ok(view)`. Else
     remove the id from `running`, set `session = HeldSession { session, by: Some(req.request) }`,
     `kept` (`Token { by: Some(id) }` when kept), `notice = None`, `revision += 1`, publish
     `Event::Account(view)` **while holding the state lock** (the last frame equals the state, as
     `set_internet` does at `app.rs:467-480`), report ok; answer `Ok(view)`.
- **`sign_in_refusal(&Door43Error) -> SignInRefusal`**, an exhaustive `match` with no catch-all:
  `Offline`, `Unreachable` → `Offline`; `AuthFailed` (401/403) → `AuthFailed`; `Server` → `ServerUnavailable`;
  `Rejected { message }`, `NotFound { message }`, `NameExists { message }` → `Rejected { reason: message }`;
  `UnexpectedResponse { reason }` → `Rejected { reason }`; `RateLimited` → `Rejected { reason: "too many
  requests" }`; `TooLarge` → `Rejected { reason: "the answer is too large" }`; `Verification`,
  `Cancelled`, `Disk`, `Setup` → `Rejected { reason: <a fixed English phrase> }`. **Never
  `e.to_string()`**: `Door43Error`'s `Display` starts with the route, and the token routes hold the
  account name (`/api/v1/users/facilitator-zq/tokens`).
- **`account/cancelSignIn`** (`Handle<CancelSignIn>`): under `sign_ins`: when `running` has
  `req.sign_in`, cancel its token, done. Else under `state`: when `session.by == Some(req.sign_in)`,
  sign that session out (`session = None`, `revision += 1`), and when `kept` is
  `Token { by: Some(req.sign_in) }`, forget on the blocking pool (failure → notice
  `signOutFailed`, `kept` stays); publish. Else push the id into `early` (cap 16). Answer `Ok(())`.
- **`account/resume`** (`Handle<Resume>` → `ResumeView`) through
  `async fn resume_kept(&self) -> Result<ResumeOutcome, ApiError>`: a session → `Resumed` with no
  request; take the lane; check again; `kept` not `Token` → `NoneKept`; note `revision`;
  `client.session_for_token(token.clone())`; revision moved meanwhile → `NoneKept`, change nothing;
  `Ok` → `session = HeldSession { by: None }`, notice none, publish → `Resumed`; `AuthFailed` →
  forget (blocking pool; a failure is reported, the outcome stays `Refused`), `kept = Nothing`,
  notice `savedRefused`, publish → `Refused`; any other error (the switch off meanwhile included) →
  notice `savedUnchecked`, publish → `Unavailable`. Never `keychain.read()` (A3's
  `the_keychain_is_read_once_at_start`).
- **`account/signOut`** (`Handle<SignOut>`): `session = None`, `revision += 1`; forget on the
  blocking pool: ok → `kept = Nothing`, notice none; error → `kept` unchanged, notice
  `signOutFailed`, `ReportOp::Keychain` failure; publish; answer the view. No request.
- **`account/profileLink`** (`Handle<ProfileLink>`, a NET `profile` query): the session's username

  segment (`path_segments_mut().push(...)`), parsed with `WebUrl::parse`; no session →

pub enum SignInNext {
    Nothing,
    /// Signed in: run the step that waited for it.

    pub fn answered(&mut self, flow: u64, request: RequestId, reply: Result<AccountView, ApiError>) -> SignInNext;
    /// Cancel, Escape, ✕, the scrim: closes; the sign-in on its way, to name in `cancelSignIn`.
    pub fn cancel(&mut self) -> Option<RequestId>;

## 7. Traps found while planning

1. `Unavailable(Feature::Account)` is asserted in `tc-app/tests/app/internet.rs:79,111,135` and
   `dispatch.rs:508`; deleting the variant breaks them on purpose (step 3).
2. `TestApp`'s `door43` is `http://127.0.0.1:9` (`common.rs:488`): after A8 a sign-in dials it. On
   Linux the refusal is immediate; never write a test that expects a sign-in to succeed there, and use
   a bound-then-dropped port for "unreachable" (a closed port can take seconds on Windows).
3. `AccountView` literals in seven places and the exact JSON in `hello_answers_real_state` (step 2).
4. `MemKeychain`'s `NoKeychain` read changes from `Ok(None)` to `Err(NoKeychain)`; update
   `keychain.rs::without_a_keychain_keep_is_refused`.
5. `#[expect(dead_code)]` on `AccountState.kept_token` (`account.rs:128-130`) fails clippy once used.
6. Never format a `Door43Error` for a person or a report: its `Display` starts with the route, and
   `/api/v1/users/<login>/tokens` names the account.
7. A fault's `path` is a prefix: `/api/v1/user` also matches `/api/v1/users/…` and
   `/api/v1/user/orgs`. Use `times: 1` and mind the order of the mint's calls.
8. Chromium logs a failed load (an aborted request, a 4xx or 5xx) as a console error, which fails a
   capture and a journey. Fulfil `net/set` with a 200 `err` body, and log A5's `net_set` failure
   with `console.warn`.
9. The token name must stay `translationCore` (J11 2 asserts it). Two computers on one account
   replace each other's token at each sign-in; tC4 does the same.
10. `test/reset` must sign out and reset the test keychain, or one captured screen's sign-in leaks
    into the next.
11. A Cancel can reach the server before its sign-in: remember cancelled ids.
12. Lock order `sign_ins` → `state`; never hold a `std::sync::Mutex` across an `.await`; keychain
    calls on the blocking pool, outside the locks.
13. The sign-in handler runs on the reply cache's own task (`dispatch.rs:180-195`), which survives
    a dropped connection: cancellation is the account's `CancelToken`, not the HTTP request.
14. A reply of a command is cached by its `RequestId`: one id per press; the re-ask after
    `NeedsInternet` sends the same body with the same id (that refusal is never cached). A
    `profileLink` is a query: nothing is cached.
15. `AppDeps` literals need the cfg field `test_keychain`; tests that swap `deps.keychain` must set it
    to `None`.
16. `boot.js` buffers only tracked editors; never track M12's inputs. `SignInForm`'s `Debug` must
    redact the password (assert messages print it otherwise).
17. Leptos `<form on:submit>` must `prevent_default()`, or the page reloads and drops every state.
18. The DS `TextField` has no `type` prop: pass `type` and `autocomplete` through `attrs` (tC4's
    login input has no `type` attribute at all).
19. `release_has_no_test_hooks` (`tc4/tests/release.rs`, ignored by default) must list
    `test/keychain`.
20. The fake needs `git` on `PATH` (`FakeDoor43::start()`), in tc-app's tests too now.
21. `start_seeded()` already has an `es-419_gl` organization: use `parity_account` with `start()`
    only.
22. `/home/bot/unfoldingword/translationcore4` has no `node_modules`; `tc4-ref` is another session's
    (§0.4).
23. The share-signin focus: tC4's ✕ is `.focused`. Opening from the menu, the menu's Layer gives
    the focus back to the trigger while M12's Layer takes it: A5's About opens from the menu the
    same way and compares equal, so follow its `choose(...)` path; if `.focused` lands elsewhere, fix
    the view, not the comparison.
24. The fake's control port and API bind 127.0.0.1 only.
