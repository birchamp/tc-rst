# E2: USB exchange

## Goal

"Save work for a teammate" writes an exchange file into a folder the person chooses, verifies it
from the device, and only then says "You can remove the stick". "Receive work from a file" names
the file's project, asks to confirm, takes the work in whole or not at all, and shows the
Received sheet, which reads again after a `Resync`. A receive never runs beside a sync of the
same project. A browser can upload an exchange file of up to 4 GiB. The export menu's Scripture
Burrito zip (J7) is the same file.

A receive takes in work only from the file's packs. The app's own record is the project (owner
ruling `rulings/2026-10-21-outside-edits.md`, rule 1). So a book file someone edited by hand
inside the exchange file never enters the project on its own. The Received sheet says so once,
nothing is kept and nothing is offered for import (`rulings/2026-10-22-H22.md` part 3). The file
on the stick is never changed.

Carried files (an audio recording, OBS front matter) travel as X built them (STORAGE §10.2 R5,
unchanged by the delta). When both people changed the same carried file, both files stay on disk
after the receive, and the Received sheet points to the conflict review. There C7b offers *Keep
this one* and *Keep both* (`rulings/2026-10-21-carried-files.md`, rule 3). E2 builds no carried
choices of its own. Carried files work now (`rulings/2026-10-22-H19.md`, option A).

## Why it matters to a translator

Teams without good internet pass their work on a USB stick. If the app said "remove the stick"
before the file was really on it, or took in half a file, a translator's work would be lost
without anyone knowing.

## Funnel card

- **Invariants**:
  - INV-REMOVE-THE-STICK-ONLY-AFTER-VERIFY: "You can remove the stick" shows only after the
    written file was read back from the device and passed every check (STORAGE §10.1 E5).
  - INV-RECEIVE-IS-WHOLE-OR-ABSENT: a receive takes in every valid entry of the file or, when it
    stops, leaves the project as it was; a damaged entry is reported, never written (§10.2 R4).
  - INV-NEVER-BESIDE-A-SYNC: a receive or an export of a project never runs while a sync of that
    project runs (A-31, AD31).
  - INV-VALID-BURRITO: every exchange file the app writes is a valid Scripture Burrito (P5).
  - INV-RECEIVE-TAKES-ONLY-PACKS: a receive takes work into the project only from the file's
    packs. A derived file in the zip that differs from what its packs give never enters the
    project without a person's choice, and the zip is never changed (OE 1; delta §2.13, I13).
  - INV-BOTH-RECORDINGS-STAY: when a receive brings a carried file that replaced the same version
    as this project's, both files stay on disk until a person chooses (CF 3; delta row L151).
- **Wrong states**:
  - The stick sentence while the verify runs, or after it failed (E5 deletes the bad file).
  - Half of a file's packs taken in after the app stopped mid-receive.
  - A receive started during a sync of the same project.
  - An empty Received sheet after a `Resync` (the event was missed).
  - A teammate's audio file changed or missing after a receive (#705).
  - An exchange file over 512 MiB refused in a browser, or a 5 GiB file sent before its size
    is checked.
  - Two zip writers: the J7 Burrito zip and the exchange file made by different code.
  - A book file edited by hand inside the zip shows in the project as changes, with no question.
  - A hand edit inside the zip found, then no notice: the translator never learns it was left out.
  - A teammate's recording silently replaced by another's after a receive, or one of two
    recordings in conflict missing from the folder.
