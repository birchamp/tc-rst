# D2: Exports

## Goal

The Community Checking export menu works: aligned USFM, plain USFM, OBS Markdown, and the print HTML
the PDF is made from. Each export runs as a job, checkpoints first, warns while conflicts are open,
and writes only outside the project. A verse whose alignment needs review keeps its stored bytes and
is named (at most 20 names, with the total). The preview and the PDF print from one print model. The
Burrito zip is the exchange file E2 builds (`docs/APP-DESIGN.md:3413`; STORAGE §10.1, last
paragraph); its menu item stays off until E2 turns it on with that one producer.

## Why it matters to a translator

Exporting is how the translation leaves the app for print and publishing. An export must never
change the project, and must never drop a verse's alignment without saying so.

## Funnel card

- **Invariants**:
  - INV-AN-EXPORT-NEVER-WRITES-THE-PROJECT: an export reads the project and writes only into the
    downloads folder; after the checkpoint that runs first, every project file is byte-identical
    before and after the export (tC4 J7: "MUST NOT: write anything else into the project").
  - INV-NO-ALIGNMENT-DROPPED-SILENTLY: aligned USFM weaves a verse's alignment only when
    `tc_align::needs_review` (`crates/tc-align/src/value.rs:108`) is false and its words match; any
    other verse keeps its stored bytes, and a verse skipped for review, inline `\zaln` or a refused
    weave is named in the export's facts (tC4 e2bfd8c3, #796). A record with nothing placed exports
    the stored bytes and is not named.

    `crates/tc-api/src/model/print.rs`; the preview and the print HTML both use it.
