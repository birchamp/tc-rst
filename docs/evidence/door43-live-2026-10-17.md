## Step 6: Door43's real answer to a push without write access (2026-10-18)

**Door43 does not answer such a push with HTTP 403.** Every HTTP status is 200. The refusal
comes inside git's own reply, as a rejected ref with a message from Gitea's pre-receive hook.
So the rebuild's assumption, that a push without write access is an HTTP 403 (tC4 issue #710),
is wrong for Door43. `tc-door43-fake` answers it with a 403 (`crates/tc-door43-fake/src/api.rs`,
the `ReceivePack` arm), so it does not behave like Door43 either.

How it was found. Git for Windows on the owner's laptop, against `https://git.door43.org`
(nginx/1.30.5, `Www-Authenticate: Basic realm="Gitea"`). `GIT_TRACE_CURL` with
`GIT_TRACE_REDACT=1`, so no trace holds a credential, and none is recorded here.

1. `push --dry-run` signed in as the owner, to `unfoldingWord/en_tn` and then to
   `lmeline/test2`: `GET .../info/refs?service=git-receive-pack` answered 401 without a
   credential, then 200 with the ref advertisement. The owner's account seems to be a Door43
   admin, so it shows nothing about a refusal.
2. The same dry run to `lmeline/test2`, signed in as `tst_win`, a plain test account the owner
   made for this: 200 again. **Door43 does not check write access at the advertisement**, so a
   dry run can never see the refusal.
3. One real push signed in as `tst_win`: a 217-byte pack holding one throwaway commit, to a
   new branch `tc-rst-403-probe` of the owner's own repository `birch/test`, where `tst_win`
   has no write access. The owner approved the push and ran it.

The refused push, request by request:

| Request | Status | Content-Type | Body |
|---|---|---|---|
| `GET /birch/test.git/info/refs?service=git-receive-pack`, no credential | 401 | `text/plain; charset=utf-8` | `Unauthorized.` |
| the same, as `tst_win` | 200 | `application/x-git-receive-pack-advertisement` | `refs/heads/master` and the capabilities `report-status report-status-v2 delete-refs side-band-64k quiet atomic ofs-delta push-options object-format=sha1 agent=git/2.54.0-Linux` |
| `POST /birch/test.git/git-receive-pack`, as `tst_win` | 200 | `application/x-git-receive-pack-result` | 151 bytes, below |

The POST's body, in pkt-lines. The error lines are on side band 2, so git prints them as
`remote:` lines. The status report is on side band 1:

```
error:
error: User permission denied for writing.
error:
unpack ok
ng refs/heads/tc-rst-403-probe pre-receive hook declined
```

Git printed `! HEAD:refs/heads/tc-rst-403-probe [remote rejected] (pre-receive hook declined)`
and `error: failed to push some refs`, and exited 1. The pack was unpacked on the server and
then thrown away. After the push, `GET /api/v1/repos/birch/test/branches/tc-rst-403-probe`
answers 404, so no branch was made.

What follows for the rebuild:

- "No write access" on a push to Door43 is a ref rejected with `pre-receive hook declined`
  and the side-band text `User permission denied for writing.`, inside an HTTP 200. libgit2
  reports that through the push's ref-status callback, not as an HTTP error.
- The fake should answer the same way, a 200 with that report, so tests exercise the path
  Door43 really takes.
- The other header facts: Door43 sets a `dcs_session` cookie on every reply, and its CORS
  headers allow only `GET`.
