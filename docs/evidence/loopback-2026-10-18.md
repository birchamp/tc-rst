# Loopback round trip of `tc4 serve` from a wasm `fetch` (2026-10-18)

Unit A2 (docs/APP-DESIGN.md §8.3, AD18, A-14). The aligner's click is a round trip: the UI
sends one request, the server answers with the verse's view, about 20 KB of JSON, and the UI
parses it. The click must be painted within 30 ms (PERFORMANCE.md, "Aligning"). This file
measures the part of that which belongs to `tc4 serve` and the browser's `fetch`, twice:

- **plain**: the page sets `X-Tc-Token` itself on every request, as the UI does (AD11);
- **proxy**: the page sets no token and a request interceptor adds it to every request,
  `/api/` included. That is the cost if the shell's header filter could not leave `/api/`
  out. G0 found that it can, so AD11 holds; this is the price of the fallback.

**What this is not.** It is headless Chromium on Linux: no Electronite, no Windows, no
Defender, no paint. G0 measured those (`electronite-spike-2026-10-17.md` on the reference
laptop, `electronite-spike-linux-2026-10-17.md` in this container). This is `tc4 serve`'s own
cost, with its real security layer and routing and the stand-in backend's `test/echo`, plus
Chromium's `fetch` and wasm's parse of the reply with `tc-api`'s types.

## The two figures

| Mode | Samples | Median | **p95** | Max |
|---|---:|---:|---:|---:|
| plain | 1,000 | 3.5 ms | **5.2 ms** | 19.1 ms |

| Node, no browser (baseline) | 500 | 0.62 ms | 1.11 ms | 2.24 ms |

Both p95 figures are under the 30 ms budget. Times are from the request to the reply parsed,
nearest-rank percentiles, after 50 warm-up clicks per pass. `performance.now()` in a page that
is not cross-origin isolated has a resolution of 0.1 ms.

The passes alternate (plain, proxy, proxy, plain), as G0's did, so drift on the shared
machine hits both modes alike. The proxy handler saw 550 `test/echo` calls in each proxy pass
(50 warm-up and 500 clicks), so every measured request went through it. The raw samples are in
`loopback-2026-10-18/results.json`.

## Reading

- The server and loopback alone cost about 0.6 ms at the median (Node, one kept-alive
  connection). A wasm `fetch` in Chromium costs 3.5 ms at the median, of which the browser's
  request handling, `response.text()`, and the parse in wasm are the rest.
- The interceptor adds about 2.2 ms at the median and 3.4 ms at p95: Chromium pauses each
  request and hands it to a JS handler in another process, which sends it back. That is the
  shape of Electron's `onBeforeSendHeaders` listener (a hop to the main process's JS and
  back). It is a lower bound for Electron: its main process also does the window's other work,
  and G0 found that a busy main thread delays every request by up to its blocking time.
- G0, in Electronite, with the filter, alone: reply p95 3.2-3.5 ms on the reference Windows
  laptop and 9.6-9.9 ms in this container (stand-in server, Xvfb, software rendering); painted
  p95 22.4-22.9 ms and 24.5-25.9 ms. This run's plain p95 of 5.2 ms sits between the two reply
  figures. The reply is a small part of the painted time, whose frame p95 was 20-22 ms in
  every Windows pass. Adding the interceptor's 3.4 ms at p95 to G0's painted figures
  gives 26-29 ms: under 30 ms, but with little room. (G0's container run while pictures load
  was already over 30 ms without any proxy, 45-49 ms; that is G0's finding, not repeated here.)
- A miss of 30 ms in either mode would have gone to §11 risk 3 and Q-13. Neither missed.

## Other measurements of the unit

Debug test builds on the same machine, same session.

- **`tokio_never_blocked`** (server on one worker thread; a paced load of 4 API callers, 2
  event streams, a 256 MiB upload, 2 readers of a 5 MiB static file and a reader of a 5 MiB
  download, for 3 s): the worst lateness of a 10 ms runtime sleep was 6.5, 24.9, 7.4, 11.3 and
  8.8 ms in five runs, against a bound of 50 ms plus the machine's own lateness (a plain
  thread's sleep, 2.3-8.2 ms worst). One run served about 4,200 API calls, 950 stream frames,
  154 MiB of upload, 127 static GETs and 60 downloads. With one call that blocks its worker for
  120 ms the same test reads 113-134 ms, so it can fail (`a_blocking_call_in_the_server_is_seen`).
- **A 1 GiB exchange upload** streams to disk: 1.3 s (839 MB/s) in one run and 3.5 s (310
  MB/s) in another, with the peak memory of the test process growing by 19-20 MiB (16 MiB of
  that is the test's own sending buffer). The file read back equals the bytes sent.
- **`release_has_no_test_hooks`** passes against `cargo build --release -p tc4` (3.85 MB): the
  `--test-hooks` flag is refused, the `test` rows answer 404, and the binary holds none of
  `test/crash`, `test/fieldStore`, `test/echo`, `test/quiet`. Pointed at the build with the
  hooks (4.0 MB) it fails.
- **`dev_cookie_only_in_debug_builds`** passes in a release test build of `tc-server`
  (`cargo test -p tc-server --release --test security`) as well as in a debug one.
- **The Windows build** of `tc-server`, its tests included, type-checks:
  `cargo check -p tc-server --all-targets --target x86_64-pc-windows-msvc`.
