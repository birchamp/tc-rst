# The UI's no-loss core: typing cost, writes per keystroke, panic recovery (2026-10-18)

Unit A4b (docs/APP-DESIGN.md §6.5, §6.6, §6.8; PERFORMANCE.md "UI: Typing in a verse, input to
paint, 16 ms"). This measures what the save machine, the draft buffer and `boot.js`'s capture
listener add to a keystroke, the writes a keystroke and ten seconds of typing cause, and the time
from a panic to the view-error callout after the reload. It also records the browser tests that
prove the unit's no-loss rules (`crates/tc-ui/app/no-loss.mjs`) and the release wasm's growth.

**What this is not.** Headless Chromium 141.0.7390.37 (Playwright 1.56.1, build 1194) on Linux,
on a loopback server, typing into the no-loss probe page of the `test-hooks` build
(`/?probe=fields`, two plain textareas on test fields), not a verse editor. No Electronite, no
Windows, no Defender, no GPU. The machine is the owner's Linux PC (12th Gen Intel Core i7-12700,
20 CPUs, 61 GB, Ubuntu 26.04.1; SHA instructions yes, AVX-512 no), shared with up to three other
agents' builds: load average 14.3 before the release run and 8.6 after it. Commit: the unit's
last commit on branch `p0-a4b` (the code measured is that of `88b247b` plus the NFC quick check of
the next commit).

## Typing (release: `build-app.sh --release --test-hooks`, `tc4` release with `--test-hooks`)

Twenty runs of 200 keystrokes each (4,000 samples per row), one key every 30 ms through
Playwright's keyboard, into a field that starts with 2 KB or 20 KB of text. Times are from the
`keydown` event's `timeStamp`. Nearest-rank percentiles, milliseconds.

| From the keydown to | Text | Median | **p95** | Max |
|---|---|---:|---:|---:|
| the end of the input event's handling (`boot.js`'s listener, the WebAssembly's handler, the save machine) | 2 KB | 0.9 | **1.3** | 5.4 |
| the same | 20 KB | 1.6 | **4.4** | 6.9 |
| the next animation frame | 2 KB | 1.5 | **15.6** | 20.5 |
| the same | 20 KB | 3.9 | **16.3** | 18.1 |
| `boot.js`'s capture listener alone (`tc4Boot.measure`) | 2 KB | 0.1 | 0.2 | 3.5 |
| the same | 20 KB | 0.1 | 0.2 | 4.2 |
| Control, without `boot.js`'s listener: end of handling | 2 KB | 0.7 | 1.2 | 6.4 |
| Control: next animation frame | 2 KB | 1.3 | 15.4 | 21.4 |

**Reading.** The work a keystroke costs is 1.3 ms at p95 with 2 KB of text (a verse is far
shorter) and 4.4 ms with 20 KB. The "next animation frame" column includes the wait for the
display's next frame: at 60 Hz a keystroke that lands just after a frame waits up to 16.7 ms with
no work at all, which is why the control without the listener shows the same 15.4 ms. So the
16 ms budget, read as input to paint, is met for a verse, and the 20 KB row's 16.3 ms is the
frame period, not the work (4.4 ms). The listener's own cost is 0.1 to 0.2 ms; the difference
between the 2 KB run and its control (0.1 ms at p95) is the listener and nothing else.

The first run of these figures (before the NFC quick check) had 2.1 ms and 6.6 ms at p95 for the
end of handling: the clean rule normalized both the current and the stored text on every
keystroke. `buffer::same_text` now runs Unicode's quick check first and normalizes only text that
may not be in NFC (`one_nfc_for_the_ui_and_the_server`, `texts_compare_in_nfc`). The remaining
cost that grows with the text is the browser's own: the textarea, the copy of the value into the
WebAssembly, and `boot.js`'s rewrite of the entry (0.2 ms at 20 KB).

The dev build, for comparison (information only; the budget is on release builds, PERFORMANCE
rule 5): end of handling 2.5 ms at p95 with 2 KB and 6.9 ms with 20 KB, next frame 15.7 and
17.1 ms, the listener 0.2 and 0.3 ms. The summaries of every run are in
`ui-no-loss-2026-10-18/`: `measure-release.json`, `measure-release-before-quick-check.json` and
`measure-dev.json`.

## Writes

| What | Count |
|---|---:|
| `localStorage.setItem` calls per keystroke | 1 |
| lines to the shell's mirror (`tc4Shell.bufferChanged`) per keystroke | 1 |
| saves during 10 s of continuous typing (one key every 100 ms) | 0 |
| drafts (`test/fieldDraft`) during the same 10 s | 10 |

One keystroke writes its field's one item and one mirror line, whatever the other fields hold
(one item per field, §6.6): the first draft's single map would have rewritten every buffered
field. No save goes while the person types (the field saves 2 s after the last input, or on blur),
and drafts go at most once a second (RT-20).

## Panic to callout

From the panicking keystroke to the in-app view-error callout after `boot.js`'s reload, twenty
times: median 109 ms, p95 138 ms, max 229 ms (release). Information only; no budget.

## Size of the release wasm (`tc_ui_bg.wasm`, plain build, no test hooks)

| Build | Bytes |
|---|---:|
| A4a (`docs/evidence/ui-runtime-2026-10-18.md`) | 1,166,565 |
| A4b | 1,429,647 |
| A4b with `buffer::nfc` stubbed out (once, to see the crate's share) | 1,304,912 |

The unit adds 263 KB: about 123 KB is `unicode-normalization`'s tables, the same crate and version
the server normalizes with (D12 of the plan), so the UI's clean rule and the server's stored text
agree on every character; the browser's own `normalize` follows its ICU's Unicode version and
could keep a field dirty for ever on a newly encoded character. The rest is the save machine, the
buffer, the glue, the panic hook and the view-error callout. The probe build is 1,650,886 bytes.

## The browser tests (`crates/tc-ui/app/no-loss.mjs`)

87 checks, all passing, on the dev build and on the release build:

| Case | What it shows |
|---|---|
| P0 | The plain UI holds no test hook name; the probe build does (the search is not blind). |
| P1 | A panic in an input handler keeps the keystroke: stored once after the reload. |
| P1b | The control: without `boot.js`'s capture listener the same keystroke is lost. |
| P2 | One panic with closures that trap afterwards: one reload, one counted panic, the running page's callout naming the first panic, the text saved; Back to Home shows the screen again. |
| P3 | Three panics: three page loads and no more, the static callout with the in-app callout's exact DOM, the server holds the posted draft and stored nothing; Back to Home reloads and the text is saved. |
| P4, P5 | A reload with a save in flight stores once; newer typing after it is saved next, both over the current version (RT-2). |
| P6 | A crash before the store and before the reply, then a new `tc4` at a new origin: the shell's mirror offers the entry with its save and its run, nothing is resent. |
| P7 | A failed save shows Retry and holds the navigation gate; after Retry the gate lets the person go only once the newer text is stored (FR-32). |
| P8 | The close guard: `setCanClose` follows every field, a close request saves first and answers true, or false while a save fails; no `beforeunload` under the shell; in a browser, a question only while something is unsaved. |
| P9 | A restart behind the same origin (a proxy rewrites the token, as a reused port plus a matching token would allow): nothing is resent, the entry stays for the offer, a reload restores nothing of the dead run. Control, run once with a throwaway build whose resend skips the `app/hello` check: the store held `["Stored once","Stored once"]`, so the check is what P9 tests. |
| P10 | With `sessionStorage` refusing writes, a panic shows the static callout at once and never reloads. |

Found by these tests and fixed in the unit: an aborted instance can panic again in a closure it
left behind ("RefCell already borrowed") and overwrite the cause (the hook keeps the first panic);
a `beforeunload` listener registered by the WebAssembly held `boot.js`'s reload behind "Leave
site?" (`boot.js` owns it now); a panic at boot has no project, so `boot.js` posts the drafts of
the run the page last met.

## Two tabs

The owner removed the one-tab check (A-19). Two pages on one origin share `localStorage`: each
field is its own item, and an entry is removed after a save only while it still holds the text that
save stored, so one tab never deletes another's newer text. Both tabs can still save the same
field; the second save names an older version and is kept beside the first as a conflict, never
written over it.
