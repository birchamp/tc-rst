# Loading a lexicon and looking words up

Budget (PERFORMANCE.md, Resources): load a lexicon, one JSON file per lexicon, in 100 ms once
per session, on the Hebrew lexicon (8,674 entries); then look entries up in memory, under 1 ms.

## What is measured

`crates/tc-resources/tests/lexicon_performance.rs`. Both bundled lexicons are repackaged and
installed into a temporary resource store by `install_lexicon_zip`, the packaging step's
function. `bundle/en/fetched.lock` does not exist yet, so the test confirms the archives with a
lock it builds in memory from the trees the zips themselves hold
(`crates/tc-resources/tests/common/bundled.rs`). That lock is never written anywhere, and
Door43 has not confirmed those trees.

- **Load:** `open_lexicon` on the `en_uhl` pin: it reads the install's receipt, reads its one
  content file (`lexicon.json`, 2,055,993 bytes), and parses it into memory. The first load of
  the process is timed alone; then 21 loads give the median and p95. A load's time leaves
  out dropping what it returns, because a session keeps its lexicons. The same 21 runs
  time the file read and the parse apart. The file is in the page cache.
- **Lookups:** every `strong` attribute of the UHB 3.0.0 Psalms
  (`fixtures/scale/psa/hbo_uhb/19-PSA.usfm`), 19,653 words with 19,228 numbered parts, looked
  up one by one with `Lexicons::lookup` against both lexicons in memory. Each lookup is timed.
- **Counts** (run by `cargo test` in every build): the same 19,653 lookups against the real
  `en_uhl` and against a Hebrew lexicon ten times larger (86,740 entries) probe 19,228 entries
  in both, one per numbered part, and open no file. Opening a project's two lexicons opens
  exactly two content files, one per lexicon, and later lookups open none.

## Results

Commit `4667e09` (branch `domain-lexicon`), release build, rustc 1.97.0, Linux 6.18, 4 vCPU
Intel Xeon @ 2.80 GHz with AVX-512 and without SHA instructions, 15 GiB RAM, shared with other
builds (load average 1.9 to 2.1 during the runs). Five separate processes, 2026-10-16. Times in
milliseconds unless marked.

| 1 | 26.7 | 18.1 | 27.2 | 0.69 | 19.7 | 7.1 |
| 2 | 18.0 | 15.8 | 21.6 | 0.68 | 15.3 | 4.1 |
| 3 | 17.1 | 16.4 | 26.3 | 0.68 | 15.4 | 4.0 |
| 4 | 16.7 | 16.0 | 23.6 | 0.67 | 15.4 | 4.3 |

Every load is under the 100 ms budget (the worst, 27.2 ms, is about a quarter of it), and every
lookup is under the 1 ms budget (the worst, 0.15 ms, is a preemption on the shared machine; the
p95 is under 0.5 µs). The test fails in a release build only above three times a budget: a
first load or a load p95 above 300 ms, or a lookup p95 above 3 ms (PERFORMANCE.md rule 5).

## What limits the numbers

- **The load is the parse.** Reading the file takes 0.7 ms; parsing it takes 15 to 20 ms. The
  parser reads the file twice: once for `format` and `version` only (2.3 ms, measured apart),
  so another format or a newer version is refused for that reason, and once into memory. The
  second pass allocates a string or a map for every value and key: the index (8,674 small
  objects, 335,200 bytes) and the entries (1,719,447 bytes) make about 86,000 of them, and
  those allocations are the cost. Measured apart with generic JSON values, the index alone
  took about 7 ms and the entries about 12 ms.
- **Before commit `4667e09`** the parse took about 40 ms (medians of 50 to 66 ms, which also
  counted dropping each loaded lexicon). The reader cloned every key into a set to catch a key
  that appears twice, then rebuilt each map; it now inserts into the map once and lets the
  map find a repeated key.
- **A lookup** splits the attribute at `:`, reads each part's number by tC4's rule, and probes
  one hash map per numbered part (`crates/tc-resources/src/strongs.rs`). Its cost does not
  depend on the lexicon's size, as the count test shows.
- **No hashing is on the load path.** `Installed::read` compares the file's size with its
  receipt and does not hash it (the store's rule), so a CPU without SHA instructions, such as
  the reference laptop's, loads no slower for that reason.

## Not measured here

- The reference machine (a five-year-old Windows laptop with Defender on). On it the load
  opens one 2 MB file instead of the archive's 8,677 files, which is the point of the
  repackaging; a cold disk adds the time to read 2 MB.
- Repackaging, which runs when the app is packaged or a lexicon is installed, in the
  background.

To reproduce:

```sh
cargo test --release -p tc-resources --test lexicon_performance -- --nocapture --test-threads 1
```
