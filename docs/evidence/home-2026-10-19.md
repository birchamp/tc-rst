# Home and its dialogs (unit B2), 2026-10-19

What B2's Home costs, and how its port compares with tC4's Home where the parity report cannot
show it. The Linux PC of `docs/evidence/linux-machine-2026-10-18.md` (12th Gen Intel Core
i7-12700, 20 threads), shared with other builds (load average 14 during the runs), so the times
are an upper bound. Release build of `app-b2` at `c35d1b6` plus the index change of the commit
that adds this file.

```sh
cargo run --release -p tc-app --features fixture-backend --example home_bench -- --runs 20
```

## Home's reads (summaries kept)

The memory backend, B1b's seed of the sample Bible (Jonah and Titus), and ten copies of it.

| Read | Median | p95 | Reply |
|---|---|---|---|
| `home/list`, the sample (1 card) | 0.035 ms | 0.041 ms | 441 B |
| `home/list`, ten copies (10 cards) | 0.22 ms | 0.25 ms | 3,861 B |
| `home/card`, the sample | 0.034 ms | 0.041 ms | |
| `home/card`, one of ten copies | 0.034 ms | 0.055 ms | |

Far below the proposed 50 ms for ten cards. A read costs a listing and one `peek` per card
(`metadata.json` and `.tc/sync.json` on the store; the fold's project details in memory); the
counts come from the kept summary. The count rows `a_second_home_visit_renders_nothing` and
`home_walks_no_history` (`crates/tc-app/tests/op_counts/home.rs`) hold it: a second visit
renders no book, file or conflict list and walks no history at any size.

## One summary (off the request, one job at a time)

`summary_files` and `summary_of` on the memory backend, which renders each book's USFM from the
fold through `CountingSnapshot` (the store reads the files it already wrote).

| Project | Books | Median | p95 |
|---|---|---|---|
| the sample | 2 | 0.35 ms | 0.39 ms |
| tc-corpus Psalms | 1 | 20 ms | 23 ms |
| ten times Psalms | 41 | 185 ms | 192 ms |

Background work with no budget. It grows with the books of a project by design (each book's
percentage needs its text), never with its history (`home_walks_no_history`). Until C1a keeps
summaries across launches, each launch computes each project's once, off the screen (§11 risk
13).

## `home/languages`

The list is compiled in (1,006,246 bytes, 9,166 rows) and indexed on its first read, which New
Bible and New Open Bible Stories ask for as they open (tC4 loads the list when the field
mounts).

| | Median | p95 | Reply |
|---|---|---|---|
| the first read: parse and index | 33-59 ms (two runs) | | |
| `a` | 5.4 ms | 7.0 ms | 7,708 B |
| `ha` | 5.6 ms | 7.2 ms | 8,024 B |
| `hausa` | 3.8 ms | 4.1 ms | 204 B |
| `es-419` | 2.7 ms | 3.6 ms | 146 B |
| `american` | 2.0 ms | 2.7 ms | 442 B |
| `zzzzqqq` | 2.3 ms | 3.2 ms | 40 B |

1,000 runs each, through `App::call`'s bytes. A query scans every row's names (tC4's
`suggestLanguages` does the same in the page); a one- or two-letter query also offers a code for
each of its 100 rows (Q35's check against the schema), which is most of its extra time. The
first measurement, before the index kept each name's words with their leading space, was 6.5 to
7.6 ms. The field's own budget is 16 ms from a keystroke to its paint (PERFORMANCE); the reply
takes at most half of it here, and the field drops a reply for an older value, so a slow reply
never shows over a newer one. On the debug build the journeys run, the first read takes about
1.8 s, which is why the field asks for the list when it mounts.

## The port where the report cannot show it

The seed check still refuses the OBS sample (`state-seed-check-2026-10-18.md` §4.1-4.3), so the
Rust Home lists only the Bible project and every B2 row with tC4's OBS card `differs`
(`parity/app/residuals.json`). Two checks, by script, on the committed captures:

- **DOM.** With tC4's OBS card taken out of its snapshot (and the asset paths the gate
  normalizes), every B2 screen and case is line for line tC4's, each line carrying its
  computed styles: `home` (74 lines), `add-project` (143), `new-bible` (149), `new-obs` (146),
  `import` (135), `add-book` (116), `account-menu`, `app-language`, `help`, `about`, `feedback`,
  `license`, `net-failed` (its dialog id aside, which the gate renumbers), `home-resume`,
  `home-empty` (the same row). The differences left are the build's version text (About and
  Feedback's attachment, masked) and `home-list-error`'s diagnosis. The Bible card alone is
  44 lines, equal to tC4's. The first comparison found one difference, fixed before the
  captures were committed: `view!` wrapped each path of the Door43 card's icon in a `<g>`; the
  icon (and the conflict chip's) is now built with Leptos's SVG builders, as the design system's
  are.
- **Pixels.** The region above the cards (the top bar, the title, the section row with
  `+ Add a project`) is pixel for pixel tC4's (0 of 256,000 pixels differ). The Bible card,
  compared with tC4's card 221 px lower, differs in 2,609 of 181,300 pixels, all on glyph and
  border edges: anti-aliasing of a card drawn at another fractional offset (tC4's OBS card is
  not a whole number of pixels high).

The plan's stronger check, a tC4 Home captured without its OBS project, was not run: the DOM
equality with computed styles and the pixel equality above the cards leave nothing for it to
find that the shift does not explain.
